Cryptographic design

Every key from 24 words. Only the phone holds the root.

Every key comes from 24 words. The phone holds the root and derives a key per object. A machine gets a key only after the phone approves, sealed so that only that machine's one-time key opens it. The relay carries sealed messages and sees no keys.

Describes protocol version 1 at revision {{protocol.rev}}, for sealctl {{release.version}}, which is in development. Items the protocol marks as planned carry a Planned pill.

Derivation tree

derive(root, label) is HKDF-SHA256 of the root with "sealctl/v1/" and the label. Keys in sealing-wax colour open data; keys in ink sign or identify.

The id is generated and read from the object itself; no hostnames, users or labels enter the derivation. An encrypted object plus the 24 words is enough to open it.

One approval, as a sequence

The six hops of one approval and what the relay sees at each
HopWhat happensRelay sees
1The machine makes a one-time key, signs the request with its pairing key and seals it with HPKE to the phone's box key; signs the relay call; opens a WebSocket wait.Machine public key, request id, size, time, network address
2The relay checks the signature and the pairing, holds the sealed request in memory, and tells the phone over its socket. Push through APNs and FCM Planned carries only the type, the request id and its expiry.Which phone it goes to; the sealed string
3The phone opens the request, shows the card, and derives the key after the tap.Nothing
4The phone seals the key with HPKE to the machine's one-time key, signs the reply with its identity key, and posts it.Phone public key, request id, size, time, network address
5The relay passes the sealed reply to the waiting socket and forgets both. The approval path writes nothing to storage.That a reply was delivered
6The machine checks the phone's signature, opens the reply with its one-time key, wipes the one-time key, and keeps the key in memory.Nothing

Because the one-time key lives only in memory until the reply arrives, a machine stolen later cannot open a reply someone recorded. The relay never sees the request content or the key.

What the relay sees

The relay routes sealed strings by public key. Everything that says what is being done sits inside HPKE ciphertext sealed to the phone's box key or to a one-time key.

The network address is used in memory while serving a call. Comparing the phone's and the machine's addresses, as keyed hashes, gives the near flag Planned; no address is stored.

The phone's backup on the relay is sealed with the state key, which comes from the root.

  1. A value is opened when a command uses it and goes into that command's environment; the store key stays in memory for the session.
  2. Public keys, machine names, OS and model, when each machine last called, request ids, sizes and times. The network address only in memory while serving a call; it is not stored.
  3. A push carries only the type, the request id and its expiry; the app fetches and opens the sealed request itself.
  4. The phone hands out keys; secret values live in sealed files on the machines.
  5. The root is readable only while the phone is unlocked. The phone keys are readable after the first unlock, so a locked phone can open a request to show it on the lock screen, but they cannot make any derived key. App spec, key storage.
  6. The words open an object when they have the object: a sealed file, a volume, a repository, or the phone's state blob from the relay.
  7. Locked or powered off, the laptop holds only sealed files. During an open session, past the screen lock, keys in memory are usable.

Confirmation levels

The level of asking says when the phone is asked; the confirmation level says how hard the approval is. The phone computes the level and applies the higher of its own and the machine's; a machine can raise its level, never lower it.

Levels don't change which keys a machine can get. They make deliberate the steps that remove sealctl's protection or are hard to undo.

The number match: the terminal shows a two-digit number exported from the request's HPKE context; the phone offers three. A wrong pick holds that machine's sensitive requests for an hour. The relay holds a delayed approval for its hour Planned.

What is deliberately not protected

  • A process given a key can leak it.
  • Malware can use what is open while the session is open.
  • A thief who gets past the screen lock during an open session.
  • A thief with the phone and its passcode.
  • Copies an attacker already took before a change of words.
  • The relay operator can see metadata (which machines ask, when, from which network address) and can withhold or delay messages, but cannot forge a phone's reply or read a key.
  • No independent audit yet.
